# AI Code Rule Checker: 文脈理解メカニズムと品質の根拠

本ドキュメントでは、「AI Code Rule Checker」がどのようにしてソースコードの**文脈（コンテキスト・意味論）を理解**し、従来の静的解析（Linterや正規表現）を超える高精度なルール検証を実現しているのか、その技術的背景と論理的根拠を解説します。

---

## 1. 根本的な仕組み：トランスフォーマーの「自己注意機構（Self-Attention）」

従来の静的解析ツールと生成AIの最大の違いは、**「すべてのコード片が互いにどう影響し合っているかを全方位で同時に計算している」**という点です。

```
[従来の解析: 局所的・ルールベース]
1行目: WORKING-STORAGE SECTION.  → 構文OK
2行目: EXEC SQL ... END-EXEC.     → 構文OK
3行目: STOP RUN.                  → 構文OK
※ 各行を個別に評価するため、行をまたぐ因果関係や状態遷移が見えない

[本システムのLLM: 自己注意機構 (Self-Attention)]
「STOP RUN」を解釈する際、
  ├── 過去に実行された「EXEC SQL SELECT」と強力に関連付け（Attention）
  ├── 「トランザクションがコミット/ロールバックされていない」という状態を認識
  └── 「:EMP-NAME」と「WORKING-STORAGE」の未定義関係を双方向リンクで検出
```

LLM内部では、コードを単語単位（トークン）に分解した後、**「どの単語が、他のどの単語と意味的に結びついているか」を行番号に関係なく全方位（N対N）で重み付け計算**します。
これにより、数十行離れた場所にある変数宣言と処理の因果関係を、人間のエンジニアと同じように「一連の流れ」として捉えます。

---

## 2. 「規約」と「コード」を同一空間でクロス検証するロジック

本システムでは、`checker.py` のプロンプト生成エンジンにおいて、**「規約JSON定義」と「ソースコード」を単一のコンテキストウィンドウ内に統合**してモデルへ渡しています。

これにより、AI内部のニューラルネットワーク上で**クロスアテンション（相互参照）**が発生します：

1. **規約の意図解釈**:
   - `COBOL-002: トランザクション制御を行うこと` という規約を読んだ時点で、AI内部では「`COMMIT`」「`ROLLBACK`」「`SQLCODE`」「`終了処理（STOP RUN / EXIT PROGRAM）`」に対する注目度（重み）が急上昇します。
2. **コードの文脈スキャン**:
   - その高まった注目度を維持したまま対象コードを走査するため、「`STOP RUN` の手前に `COMMIT` が存在しない」という**欠落（不在）の文脈**を正確に検知できます。

## 3. 文脈理解を証明する具体例

構文チェック（Syntax Check）だけでは絶対に不可能で、**文脈理解（Contextual Understanding）があるからこそ成立する実例**です。

### ① トランザクション境界の理解（Pro*COBOL / Pro*C）
- **構文レベル**: `EXEC SQL SELECT ...` も `STOP RUN` も文法的に100%正しいCOBOLコードです。構文エラーは出ません。
- **文脈理解**: 「SELECTを実行した後にプログラムを終了すると、DBMS側でカーソルやロックなどのトランザクションが中途半端な状態で保持され、他バッチや整合性に悪影響を及ぼす」という**業務的・システム的な文脈（副作用）**を理解しているため、「違反」と判断して修正案（`IF SQLCODE = 0 ... COMMIT`）を提案できます。

### ② ホスト変数からの「逆算推論」（意味論的補完）
- **構文レベル**: 規約JSONには「変数定義漏れをチェックせよ」とは一言も書いていません。
- **文脈理解**: SQL内のホスト変数 `:EMP-NAME` を見ると、AIは「ホスト変数は事前にデータ部で定義されている必要がある」という言語仕様の文脈を自律的に連想します。そして `WORKING-STORAGE` の中身を遡って探索し、定義が存在しないことを見抜いて「`01 EMP-NAME PIC X(30).` を追加してください」と指摘します。

### ③ C言語における「因果関係の追跡」（バッファサイズとポインタ）
```c
void process_data(char *input) {
    char buffer[64];
    strcpy(buffer, input);
}
```
- **構文レベル**: `strcpy` の引数は `char*` 同士であり、型チェックや文法チェックはパスします。
- **文脈理解**:
  - `buffer` の宣言サイズ（64バイト）を把握。
  - `input` が関数の外部から渡される未知の長さのポインタであることを把握。
  - 「未知の長さを固定サイズ64の領域に境界チェックなしでコピーしている」という**2行間の因果関係**を結びつけ、バッファオーバーフロー脆弱性として検出します。

## 4. 従来のLinter（静的解析）との比較まとめ

| 比較項目 | 従来の静的解析（Linter / AST） | 本システム（生成AIモデル） |
| :--- | :--- | :--- |
| **評価単位** | 単一の行、または局所的な構文木ノード | **ファイル全体の処理フローと因果関係** |
| **評価基準** | 定義されたパターンの完全一致 | **規約の「意図」とコードの「実行結果（副作用）」** |
| **欠落の検知** | 指定構文が「有るか無いか」の単純判定 | **「この処理をしたなら、次にあれが必要」という文脈的欠落の推論** |
| **指摘の質** | 「エラー: 行8にCOMMITがありません」 | **「なぜCOMMITが必要か、放置すると何が起きるか、どう直すべきか」** |

## 5. システム設計による品質と安全性の担保

本システムはAIモデル単体に依存するのではなく、前後のシステムアーキテクチャによって高い品質を保証しています。

1. **インジェクション・フォーマットエラー耐性**:
   プロンプトや規約JSONに中括弧 `{ }` や正規表現が含まれていても、安全な明示的プレースホルダ置換によって例外を未然に防止。
2. **メモリ上での即時破棄（機密保護）**:
   受信したソースコード・規約ファイルはディスクに保存されず、ストリーム読み込み完了と同時に明示的な `.close()` により破棄。
3. **長文推論に対応したタイムアウト設計**:
   大規模な業務プログラム（COBOL等）や深層推論モデルにも耐えうる 300 秒の非同期タイムアウト設定。
4. **完全オフライン動作（RHEL閉域網対応）**:
   フロントエンド資産をコンテナ内に内包し、外部通信遮断環境でも全機能が正常動作。
